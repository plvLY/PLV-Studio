## 1. 项目概述

**PLV PermMap** 是一套面向 Java 项目的可复用权限管理系统，提供统一的权限配置、Spring Boot 集成、后端授权执行和可视化调试能力。

核心定位：**为 Java 项目提供可复用的权限管理能力，并通过可视化配置和授权调试提升开发效率。**

项目优先解决自身开发时缺少现成权限系统的问题，首版聚焦基础 RBAC、菜单与 API 资源管理、后端授权、权限关系可视化和独立业务项目集成。

## 2. 核心目标

- 建设一套可复用的 Java 权限管理基础能力，不必每次新项目都从零编写权限模块
- 通过可视化管理平台降低权限配置和调试成本
- 通过 Spring Boot Starter 让业务项目以最小代码量接入权限能力
- 打通完整流程：创建用户 → 创建角色 → 配置资源 → 分配权限 → 接入业务项目 → 执行授权 → 查看授权结果
- 作为独立的个人作品集项目展示

## 3. 产品形态

产品由两个相互配合的部分组成：

### 部分一：权限管理平台
提供可视化管理界面，用于维护权限对象和授权关系：
- 用户管理（列表、新增、修改、状态、角色关联、权限查询）
- 角色管理（列表、新增、修改、状态、用户分配、资源授权）
- 菜单资源管理（层级结构、前端功能入口）
- API 资源管理（HTTP 方法 + 路径模式、后端接口访问权限）
- 权限关系可视化（用户 → 角色 → 资源 关系图）
- 授权调试工作台（测试用户、HTTP 方法、API 路径，展示允许/拒绝原因）

### 部分二：Java 权限组件
为业务项目提供可复用的权限能力（通过 Spring Boot Starter 集成）：
- 身份与授权上下文衔接
- 用户和角色关系读取
- API 访问权限校验
- 方法级权限校验
- 权限数据查询接口
- 权限缓存与更新机制
- 与 Spring Boot 项目的集成能力

## 4. 技术架构

### 架构模式
- **模块化单体**：管理后台、应用服务和权限核心运行在同一 Spring Boot 应用中
- **权限核心独立**：`permmap-core` 不依赖特定数据库、前端框架或业务用户表
- **双模式适配**：统一管理模式（平台配置 + Starter 使用）+ 本地存储模式（业务项目自有数据源 + Starter 接入）

### 核心模块结构
```
plv-permmap/
├── permmap-core/              # 权限核心领域与授权判定
├── permmap-application/       # 管理用例与应用服务
├── permmap-infrastructure/    # 数据库持久化与数据适配
├── permmap-admin/             # 管理平台后端入口
├── permmap-spring-boot-starter/  # 业务项目集成 Starter
├── permmap-demo/              # 独立示例业务项目
├── permmap-frontend/          # Vue 3 可视化管理前端
└── docs/                      # 产品与技术文档
```

## 5. 核心领域模型

采用 RBAC（基于角色的访问控制）模型，引入 `Application` 概念隔离不同业务系统：

```
Application
    │
    ├── User ───── UserRole ───── Role
    │                               │
    │                               │
    │                          RoleResource
    │                               │
    │                               │
    └── Resource ◄───────────────────┘
```

核心实体：
- **Application**：接入的业务应用（如 `order-service`、`content-service`），通过 `application_code` 标识
- **User**：权限系统中的用户主体，含外部身份标识 `external_user_id`，与业务用户表通过 `external_user_id` 关联
- **Role**：角色，按应用隔离，使用稳定的 `role_code`，同一应用内 `role_code` 唯一
- **Resource**：菜单或 API 资源，通过 `resource_type` (`MENU`/`API`) 区分
  - 菜单资源使用 `parent_id` 构建层级结构
  - API 资源通过 `http_method` + `path_pattern` 精确匹配（如 `GET /api/orders/{id}`）
- **UserRole**：用户与角色关联，同一应用内用户-角色组合不得重复
- **RoleResource**：角色与资源关联，同一角色-资源组合不得重复

### 5.1 关键设计约束

| 设计领域 | 约束说明 |
|----------|----------|
| **Application隔离** | 资源、角色和应用内用户默认归属于对应应用范围，防止跨系统权限混用 |
| **角色编码** | 同一应用内 `role_code` 唯一，用于业务配置和集成，不依赖角色名称 |
| **资源匹配** | API 资源必须明确匹配规则，不能采用不受控的字符串包含匹配 |
| **用户标识** | `external_user_id` 不应被强制解释为用户名，同一应用内外部用户标识应保持唯一 |
| **禁用状态** | 禁用的角色不能继续作为有效授权依据，禁用的用户不得继续使用其授权 |

## 6. 设计原则

PLV PermMap 的核心设计遵循以下原则，对应产品文档中的 `3.1-3.6` 条款：

| 原则 | 说明 |
|------|------|
| **可复用优先** | 权限管理能力必须能被不同 Java 项目重复使用，而不是只在 PermMap 管理后台有效 |
| **配置优先** | 常见权限关系应尽可能通过管理界面配置，减少开发者修改代码的频率 |
| **前后端权限一致** | 前端权限控制改善交互体验，后端授权才是安全边界；隐藏菜单/按钮不能代替服务端访问控制 |
| **授权规则可验证** | 每项关键权限配置都应通过测试场景进行验证，避免只配置、不验证 |
| **技术边界清晰** | 身份认证、权限管理和业务授权需要明确区分；首版不实现完整企业级身份中心 |
| **优先服务自己的项目** | 所有功能优先围绕真实 Java 项目开发过程设计，暂不投入市场规模分析、商业化设计 |

1. 能够独立启动权限管理平台
2. 能够配置用户、角色和资源权限
3. 能够在独立的 Java 示例项目中接入权限能力
4. 后端能够执行真实的 API 授权检查
5. 前端能够查看菜单和相关权限配置
6. 能够通过可视化界面理解用户、角色与资源的关系
7. 能够使用授权调试功能验证典型场景
8. 关键授权逻辑有自动化测试
9. 能够通过 Docker Compose 启动演示环境
10. 有完整的接入文档和演示数据

## 9. 与 PLV Studio 的关系

PLV PermMap 是 PLV Studio 技术生态的重要组成部分，专注于 Java 权限管理领域。它为开发者提供：

- **新项目接入加速**：Maven Starter 依赖 + 少量配置即可获得完整权限能力
- **权限配置可视化**：不再需要在代码和数据库间反复切换
- **授权问题快速定位**：可视化调试工作台替代日志与数据库人工排查
- **技术复用沉淀**：核心授权逻辑可跨项目复用，避免重复造轮子

PLV Studio 将作为 PLV PermMap 的展示平台，提供项目文档、架构说明、技术决策记录和使用案例。
